## 2. バックボーン（計画書3.2節・3.6節）

```
入力（観測窓1秒：攻撃10人+守備10人+ボール、位置・速度）
  → 選手ごとのMLPエンコーダ（7次元特徴：位置・速度・種別one-hot、attack/defend/ball共有）
  → 時間方向エンコーダ（GRU、観測窓を1本のサマリベクトルへ集約）
  → 選手間Self-Attention（攻撃・守備・ボール全21エンティティ、paddingマスク対応）
  → デコーダ（MLP、攻撃側選手ごとに未来101フレーム分の"生の"加速度を出力）
  → 制約層（ハード制約 or 制約なし）
  → 出力：未来4秒の攻撃側軌道
```

**設計判断**：計画書3.2節の図は「時間方向エンコーダで集約した後に、各時刻でSelf-Attention」という記述で字面上やや曖昧だったため、3.6節の「最小構成でよい」という方針を優先し、GRUで観測窓を1本のベクトルに集約してからSelf-Attentionを1回だけ適用する設計にした。窓内の時刻ごとの相互作用まで表現したくなった場合は、エンコーダ直後にもう1段Self-Attentionを挟む形で拡張できる。

守備側選手は予測対象に含めず、コンテキスト（入力・スペース支配計算の固定背景）としてのみ使用する（計画書3.2節の設計通り）。

## 3. ハード制約層（計画書3.3節）

- 加速度上限：`a = a_max * tanh(ã / a_max)`（成分ごと）
- 速度上限：Euler積分＋clip（成分ごと）
- ピッチ境界：位置のclamp

`a_max=6.0 m/s²`, `v_max=9.0 m/s`（ともに仮値）。極端な入力（±1e6）でも出力が物理範囲を超えないこと、勾配がこの層を貫通して流れることをユニットテストで確認済み。

3パターン比較のため、制約を一切適用しない`UnconstrainedIntegrationLayer`（tanh射影・clip・clampなしの素のEuler積分）も同じインターフェースで実装し、`TrajectoryBackbone`の制約層を差し替え可能にした。

## 4. ソフト制約（計画書2.3節・3.4節）と実装過程での修正

### 4.1 L_compact：分散→標準偏差への変更

当初の実装は計画書の式通り $\mathcal{L}_{compact}=|\text{Var}-\text{目標値}|$（分散、m²単位、値は数十のオーダー）だったが、100エポック学習でL_data（ADE、m単位、1〜3程度）と単位が揃わず、λ=0.1でもtactic項がL_dataを上回って**精度を無視して分散だけ合わせにいく学習**になる問題が発生した。分散を標準偏差に変更（$\mathcal{L}_{compact}=|\text{Std}-\text{目標値}|$）することでL_dataとスケールが揃い、解消した。目標値は学習データの実軌道の縦方向標準偏差の平均から自動算出（`compute_target_compactness`、今回の値：約11.6m）。

なお、コンパクトネスの定式化自体は判定フェーズ（`phase0_report.md` 6節）の知見を踏襲し、全方位ではなく**攻撃方向（縦）限定**の分散/標準偏差を使っている。

### 4.2 L_space：学習損失としては機能せず、除外

$\mathcal{L}_{space}=-\sum\text{PitchControl}_{attack}$（判定フェーズの等方ガウス版pitch controlを流用、Voronoi版は微分不可能なため使用不可）を実装したが、以下の問題が段階的に見つかった。

1. **ピッチ全面平均だと勾配がほぼ消失**：大半のグリッド点は選手から遠く、両チームの影響がほぼゼロ→`sigmoid(0)=0.5`に張り付き、選手配置を変えても値がほぼ動かない
2. **対策①（選手近傍のみで平均、半径15m）**：勾配は流れるようになったが、今度は「平均」という集計が選手の密集（ガウス影響の重ね合わせ）を有利にしてしまい、計画書が意図する「広く支配する」の逆になっていた
3. **対策②（面積和＋平方根に変更）**：cell_area加重の面積和（本来の$\sum$の意図に近い）に平方根を取ってL_dataとスケールを揃えた。合成データでの単体テストでは正しい方向（散らばる方が密集より支配的）に反応することを確認
4. **それでも実際の学習では動かない**：勾配ノルムを直接比較したところ、L_data(0.107)に対しL_space(w2=0.05)は0.029、L_compactは0.00195と、いずれも小さいが非ゼロ。**w2を0.05→1.0（20倍）に上げても、近傍半径を15m→8mに絞っても、valid L_spaceは-38付近でほとんど動かなかった**（100エポック学習、λを0〜2.0で振っても同様）

**結論**：L_spaceの値自体は妥当（実軌道 -38.18、攻撃を守備に重ねた最悪ケース -35.10、ピッチ全体に広げた理想ケース -45.75、と正しい方向に反応することを個別に確認済み）だが、**バッチごとに実際の守備側配置（正解データ、固定コンテキスト）が異なるため、L_spaceの勾配方向がバッチ間で一貫せず、多数のSGD/Adamステップの中で打ち消し合って蓄積しない**と考えられる。これは「観測データとしての説明力」（判定フェーズでスペース支配が最も強い相関を示したこと）と「学習損失としての勾配の効きやすさ」が別の性質であることを示す一例である。

対応として、**`hard_soft`モードの学習損失にはL_compactのみを組み込み、L_spaceは監視用の指標（毎エポックログはする）として残す**方針にした（`scripts/train.py`）。判定フェーズの結論やL_space自体の妥当性を否定するものではなく、現在の微分可能な簡易実装が今回のデータ規模・学習設定では学習信号として機能しなかった、という実装上の制約として記録する。

## 6. λのPareto曲線（計画書6.2節、最終版）

L_compactのみを学習損失に組み込んだ状態（`w1=1.0`）で、λを0〜2.0まで振った結果。

| λ | valid ADE | valid L_compact | valid L_space（監視のみ、学習には不使用） |
|---|---|---|---|
| 0 | 2.258 | 2.134 | -38.655 |
| 0.05 | 2.366 | 2.182 | -38.635 |
| 0.1 | 2.338 | 2.164 | -38.671 |
| 0.5 | 2.374 | 2.009 | -38.691 |
| 1.0 | 2.547 | 1.835 | -38.792 |
| 2.0 | 2.718 | 1.825 | -38.746 |

λを上げるほどL_compact（目標値との乖離）が単調に改善し（2.134→1.825）、λ≈0.5あたりまでは精度への影響が軽微、λ=1.0以降で明確に精度を犠牲にし始める、という解釈可能なトレードオフ曲線が得られた。L_spaceは学習損失から外した通りほぼ一定で推移しており、想定通りの挙動。

## 7. 既知の制約・今後の課題

1. **L_spaceが学習損失として機能しない**（4.2節）。バッチ間の勾配方向の不安定さが原因という仮説だが、未検証。改善案としては、守備側配置でサンプルを層別化してバッチを組む、あるいは判定フェーズのVoronoi版に近い（だがまだ微分可能な）別の定式化を試す、などが考えられる
2. **試合単位split（5/1/1）の偏り**：validに割り当てた試合（J03WQQ）は元々成功率が低く（判定フェーズで確認済み）、valid指標の解釈には注意が必要
3. **ハード制約のハイパーパラメータ（a_max, v_max）は仮値**で、実測値からの校正はまだ行っていない
4. 今回の学習はすべてローカル(M5)での小規模実験（100エポック、345件）。計画書4.4節の運用フロー通り、本番規模の実験はColabでの実行を想定している

## 8. 追記：判定フェーズ側のspace_control.pyにも同じダイリューションバグが見つかった

本レポート4.2節で見つけた「ピッチ全面平均によるダイリューション」バグは、学習損失用のtorch実装（`soft_constraints.py`）だけでなく、**判定フェーズで使っているnumpy実装（`space_control.py`）の`isotropic_gaussian_dominance` / `velocity_oriented_dominance`にも同様に存在していた**ことが、合成データでの健全性チェック（計画書7節）で判明した。近傍半径＋面積和＋平方根という同じ考え方で修正し、判定フェーズ側の結果（`phase0_report.md` 8節）を更新している。ただし判定フェーズ側では、修正後にコンパクトネスとの交絡という別の問題が見つかり、**Voronoi占有率を主指標とする**方針に整理した。詳細は`phase0_report.md` 8節を参照。

## 9. ハード制約の価値の再検討：精度ではなく物理的妥当性の保証

5節の3パターン比較では、ハード制約ありがなしよりADEでわずかに（約2%）優れていたが、これは1回の学習のみの結果であり、乱数シードを変えた再現実験をしていないため統計的な優位性を主張できる段階にはない。ソフト制約（6節）についても、λを上げるほどADEは単調に悪化しており、これは「精度が上がる」という主張とは逆の、計画書5.3節が意図した通りのトレードオフである。

そこで、**「精度で優る」ではなく「非現実的な出力を原理的に排除できる」**という、計画書5.3節（Plausibility）に沿った主張の裏付けを`scripts/check_physical_plausibility.py`で確認した。制約なしモデル（`none_100ep`）とハードのみモデル（`hard_only_100ep`）を、学習済みの重みのままtrain/valid全件に適用し、出力が物理的制約（最大速度9.0m/s、最大加速度6.0m/s²、ピッチ境界105m×68m）を破っているかを直接カウントした。

### 結果

| | フレーム単位の境界違反 | 選手×イベント単位で1フレームでも違反 | 速度超過 | 加速度超過 |
|---|---|---|---|---|
| 制約なし（train, 345521フレーム） | 0.568%（1964件） | **1.29%**（44/3421） | 0% | 0.002%（6件、最大6.71m/s²） |
| 制約なし（valid, 79083フレーム） | 0.652%（516件） | **1.28%**（10/783） | 0% | 0% |
| ハードのみ（train・valid） | **0%（構造的に不可能）** | **0%** | **0%** | **0%** |

制約なしモデルは、選手が常にピッチ内にいる実データのみで学習したにもかかわらず、予測では実際にピッチ外（y座標は最大79.4m、幅68mを11m超過／x座標は最大106.6m、長さ105mを超過）に選手を配置してしまう。予測対象となった選手×イベントの**約1.3%で、少なくとも1フレームはピッチ外に出ている**。速度は今回はたまたま超過しなかったが、加速度は train split で6フレーム超過している。

ハード制約モデルは、同じデータ・同じ学習手順で、これらの違反が**構造上原理的に発生しない**（forward pass内のtanh射影・clip・clampが保証する）。これは統計的検定を要さない、モデル構造による保証であり、5節の弱い精度差よりもハード制約の意義を明確に主張できる根拠である。
